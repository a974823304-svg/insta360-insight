## 1. 评审目标与原则

### 1.1 目标

| # | 目标 | 衡量 |
|---|---|---|
| 1 | **守住质量底线**：P0/P1 bug 不进 main | P0 逃逸率 < 5% |
| 2 | **知识共享**：评审过程让 ≥ 1 个人了解改动 | 评审覆盖率 100% |
| 3 | **风格统一**：代码符合 [02 规范](./02-团队代码规范与最佳实践指南.md) | lint 全过 |
| 4 | **可维护**：未来人能轻松读懂 | 6 个月后回头看无"这是什么鬼" |

### 1.2 原则

1. **小批量** ≤ 400 行 diff：超过就拆。人类注意力是稀缺资源。
2. **及时评审**：24h 内首响应（详见 [§ 6](#6-评审时效-sla)）。
3. **作者自检优先**：提 MR 前过一遍 [§ 3 checklist](#3-评审清单-checklist)，自检覆盖率 100%。
4. **就事论事**：评审评论针对代码，不针对人。
5. **不阻塞非关键问题**：MINOR / NIT 不挡合入，作者可后续 PR 修。

## 2. 评审角色

| 角色 | 谁 | 职责 |
|---|---|---|
| **作者** | 提交者 | 自检、写好 MR 描述、回应评论 |
| **评审者** | 1-2 名同模块成员 | 主评审，给 BLOCKER / MAJOR |
| **领域专家** | 该模块 owner（如 AI 模块的算法负责人） | 给权威意见，必要时批准 |
| **最终批准** | Tech Lead 或 owner | 点 Approve 前确认所有 BLOCKER / MAJOR 已解决 |
| **旁观者** | 任何团队成员 | 可评论，标记为 "Optional / FYI" |

**最少人数**：
- 普通功能 MR：**1 个评审者 + 1 个最终批准**
- 涉及架构 / 跨模块：**2 个评审者 + 1 个最终批准**
- 安全敏感（Auth / 密钥 / 网络）：**必须**有 Tech Lead 评审

## 3. 评审清单 Checklist

### 3.1 通用（所有 MR）

**作者自检**

- [ ] diff ≤ 400 行（不含 lockfile / 自动生成）
- [ ] CI 全绿（lint / test / build）
- [ ] MR 描述完整（见 [§ 9 模板](#9-评审模板)）
- [ ] 测试覆盖：新增/修改的逻辑有单测
- [ ] 无新增 lint 警告
- [ ] 无调试代码（`console.log` / `fmt.Println` / `panic("test")`）
- [ ] 无注释掉的死代码
- [ ] 文档同步（README / ADR / 注释）

**评审者检查**

- [ ] **正确性**：逻辑是否对？边界条件？空数组 / nil / None 处理？
- [ ] **可读性**：命名清楚？嵌套 ≤ 3 层？函数 ≤ 50 行？
- [ ] **错误处理**：错误显式？日志带 context？用户能看到友好提示？
- [ ] **安全性**：输入校验？Auth？密钥？注入风险？
- [ ] **性能**：N+1 查询？大循环？大对象传递？
- [ ] **可测试**：依赖可 mock？关键路径有测试？
- [ ] **向后兼容**：老调用方会爆吗？是否需要 deprecation 警告？

---

### 3.2 后端 Go 专项

- [ ] handler 不直接操作 DB / mock（应走 service）
- [ ] service 返回 error，handler 转 HTTP code（不混用）
- [ ] 错误传递用 `fmt.Errorf("...: %w", err)`，保留链
- [ ] 外部调用（DB / HTTP / LLM）必须带 `context.Context` + 超时
- [ ] 没有 `panic` 做业务控制流
- [ ] 没有手写 `itoa` / `intToStr` 之类重复造轮子
- [ ] 中间件顺序正确（Recovery → RequestID → AccessLog → CORS → Auth → 业务）
- [ ] `go.mod` 跑过 `go mod tidy`（无多余 indirect）
- [ ] 公共导出有 Go doc 注释

---

### 3.3 Python 专项

- [ ] 函数签名带类型注解
- [ ] 不用 `except:` 裸捕获；`except Exception` 只在兜底层
- [ ] LLM 输出 parse 失败要**带 raw**进日志
- [ ] 不要在函数内重复 `import`（提到模块顶部）
- [ ] Pydantic schema 校验到位
- [ ] 没有 `type: ignore` 逃逸（或有 comment 解释）
- [ ] `requirements.txt` 锁版本
- [ ] pytest fixture 用 `conftest.py` 集中

---

### 3.4 Vue / 前端专项

- [ ] `<script setup>` 类型完整（开了 TS）
- [ ] Props / Emits 显式声明
- [ ] 模板不写复杂表达式（> 1 个方法调用 → 抽 computed）
- [ ] 大列表 (> 100) 用虚拟滚动
- [ ] ECharts 按需引入，不写 `import * as echarts`
- [ ] 错误处理走统一 interceptor，不在组件里 try-catch
- [ ] Store fallback 数据与后端 mock 字段一致（`make check-contract`）
- [ ] 组件不直接调 axios（应走 `api/xxx.js`）
- [ ] 没有 hardcoded 颜色 / 字号（用 theme token）

---

### 3.5 AI / LLM 专项

- [ ] Prompt 改动有 golden set 评测结果附在 MR
- [ ] 兜底链完整：LLM 失败 → 规则 → 默认
- [ ] 输出 parse 失败带 raw 日志
- [ ] 没有把 user input 直接拼进 system prompt（注入风险）
- [ ] Token 用量有上限（避免单次 prompt > 4K）
- [ ] Provider 切换不会污染全局状态（`dashscope.api_key` 等）
- [ ] 输出含敏感词 / PII 时脱敏

## 4. 评审流程

```
作者                    评审者               CI                 最终批准
 │                       │                  │                    │
 │ 1. 本地自检           │                  │                    │
 │ (checklist §3.1)     │                  │                    │
 │                       │                  │                    │
 │ 2. 推送分支 ────────► │                  │                    │
 │                       │                  │                    │
 │ 3. 开 MR ──────────►  │ 自动指派          │ 触发 CI            │
 │                       │ (CODEOWNERS)     │ (lint/test/build)  │
 │                       │                  │                    │
 │                       │ 4. 评审           │                    │
 │ ◄──── 评论/请求修改 ── │ (24h 首响应)     │                    │
 │                       │                  │                    │
 │ 5. 修改并 push        │                  │                    │
 │                       │                  │                    │
 │ 6. 回应评论 + 重新评审│                  │                    │
 │                       │                  │                    │
 │                       │ 7. Approve ────► │                    │
 │                       │                  │                    │
 │                       │                  │ 8. 最终批准 ─────► │
 │                       │                  │                    │
 │ 9. Squash merge ────────────────────────► │ main               │
```

### 4.1 分发规则（CODEOWNERS）

`.github/CODEOWNERS`（示例）：
```
# Go 后端
/backend/                     @tech-lead-backend @senior-backend-1

# AI 引擎
/ai/                          @tech-lead-ai @senior-ai-1

# 前端
/frontend/                    @tech-lead-frontend @senior-frontend-1

# 文档
/docs/                        @tech-lead-backend

# 全局配置
/docker-compose.yml           @tech-lead-backend
/Makefile                     @tech-lead-backend
```

MR 打开后自动指派到对应 owner，owner 必须评审才能 Approve。

## 5. 评审标准（分级）

| 等级 | 标识 | 含义 | 处理 |
|---|---|---|---|
| **BLOCKER** | 🔴 | 必须修：会让线上爆 / 数据错 / 安全洞 / 重大架构偏差 | 不修不能合 |
| **MAJOR** | 🟠 | 应该修：可读性差 / 性能问题 / 缺关键测试 / 错误处理不全 | 通常不修不能合 |
| **MINOR** | 🟡 | 建议修：风格问题 / 命名 / 注释 | 作者自行决定，可以后续 PR |
| **NIT** | 🟢 | 吹毛求疵：拼写、空行、标点 | 不影响合入，仅供讨论 |

**示例评论**：
```markdown
🔴 BLOCKER: `middleware.go:18` CORS 反射任意 Origin，等同关闭跨域防护。建议改成白名单。
🟠 MAJOR: `insight_service.go:58` Filter 被丢弃且没注释，未来接 ClickHouse 会出 bug。
🟡 MINOR: `kpi.go:42` 变量名 `d` 太泛，建议 `kpi` 或 `card`。
🟢 NIT: 文末多了一个空行。
```

## 6. 评审时效 SLA

| MR 规模 | 首响应 | 最终评审完成 | 备注 |
|---|---|---|---|
| ≤ 50 行 | 4 小时内 | 1 个工作日 | 简单改动 |
| 51-200 行 | 8 小时内 | 2 个工作日 | 普通功能 |
| 201-400 行 | 24 小时内 | 3 个工作日 | 中等功能 |
| > 400 行 | 必须拆分 | — | 拒绝评审，要求拆 |

**作者响应 SLA**：
- 收到评论后 **1 个工作日** 内回应（不是改完，是回应）
- 简单改动（MINOR）2 个工作日内合入
- 复杂改动（MAJOR）4 个工作日内合入

**超时升级**：
- 评审者 > 48h 未响应 → 自动 @ 备选 owner
- 作者 > 3 个工作日未回应 → 关闭 MR，留 comment 说明原因

## 7. 自动化门禁

### 7.1 CI 必跑（合并前）

| 检查 | 工具 | 失败处理 |
|---|---|---|
| Lint | `golangci-lint` / `ruff` / `eslint` | ❌ 阻断合入 |
| 单元测试 | `go test` / `pytest` / `vitest` | ❌ 阻断 |
| 覆盖率门槛 | diff 覆盖率 ≥ 70%（用 diff-cover / codecov） | ⚠️ 警告，但允许 senior approve |
| 字段一致性 | `python scripts/check_contract.py` | ❌ 阻断 |
| 构建 | `go build` / `vite build` / `pyproject check` | ❌ 阻断 |
| 依赖扫描 | `npm audit` / `pip-audit` / `govulncheck` | ⚠️ 高危阻断，低危警告 |
| Secret 扫描 | `gitleaks` / `trufflehog` | ❌ 阻断 |
| 大文件 | `> 1MB binary` | ❌ 阻断（应走 LFS） |

### 7.2 CI 配置文件（GitHub Actions 示例）

`.github/workflows/ci.yml`：
```yaml
name: CI
on: [pull_request]

jobs:
  backend:
    runs-on: ubuntu-latest
    services:
      clickhouse:
        image: clickhouse/clickhouse-server:24
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version: '1.22' }
      - run: cd backend && go mod download
      - run: cd backend && golangci-lint run ./...
      - run: cd backend && go test -race -coverprofile=coverage.out ./...
      - run: cd backend && go test -coverprofile=coverage.out ./... && go tool cover -func=coverage.out
      - uses: actions/upload-artifact@v4
        with: { name: backend-coverage, path: backend/coverage.out }

  ai:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.11' }
      - run: cd ai && pip install -r requirements.txt
      - run: cd ai && ruff check .
      - run: cd ai && pytest --cov=ai --cov-report=xml
      - uses: actions/upload-artifact@v4
        with: { name: ai-coverage, path: ai/coverage.xml }

  frontend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20' }
      - run: cd frontend && npm ci
      - run: cd frontend && npm run lint
      - run: cd frontend && npm run test -- --coverage
      - run: cd frontend && npm run build

  contract:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
      - run: python scripts/check_contract.py
```

### 7.3 合并条件（Branch Protection）

在 GitHub/GitLab 设置 `main` 分支：
- ✅ 必须有 ≥ 1 个 Approve
- ✅ 必须通过所有 CI 检查
- ✅ 必须解决所有 conversation（评论被 mark resolved）
- ✅ 分支必须 up-to-date with `main`
- ❌ 禁止 force-push
- ❌ 禁止直接 push（必须走 MR）

## 8. 评审礼仪

### 8.1 评审者 side

**DO ✅**
- "我有个疑问..." → 提出问题而非下定论
- "建议改成 X 因为 Y" → 给原因
- "这个分支里如果 Z 会怎样？" → 引导思考边界
- 区分"必须改"和"建议改"（用 [§ 5 分级](#5-评审标准分级)）

**DON'T ❌**
- "这写得太烂了" → 攻击性
- "你不知道 xxx 吗" → 居高临下
- "全改" → 不具体
- 连续提十几个 NIT 挡合入 → 适度妥协

### 8.2 作者 side

**DO ✅**
- 把"为什么"写在 MR 描述里，让评审者不用猜
- 收到评论先回应"理解了，我去改"，而不是立刻争论
- 不同意时礼貌反驳："我考虑的是 X，不过你说的也有道理，我们聊一下？"

**DON'T ❌**
- "我觉得没事" → 自我辩护
- "时间紧，先这样吧" → 牺牲质量换速度
- 在评论区吵架 → 拉到线下 / 视频会

### 8.3 文化标语

> **"Review the code, not the coder."**
> **"Disagree and commit."** —— 不同意，但既然决定了就执行。

## 9. 评审模板

### 9.1 MR 描述模板

`.github/PULL_REQUEST_TEMPLATE.md`：

```markdown
## What
<!-- 一句话说清改了什么, e.g. "给 AI engine 加 retry + circuit breaker" -->

## Why
<!-- 为什么改, 关联 issue / ADR / 业务背景 -->
<!-- 例: "线上偶发 LLM 5xx 导致全部走兜底, 体感 AI 不稳定; 详见 issue #123" -->

## How to test
<!-- 怎么验证 -->
<!-- 例: -->
<!-- 1. cd backend && go test ./... -->
<!-- 2. 启动 dev, curl /api/kpi -->
<!-- 3. 模拟 dashscope 抛 TimeoutError, 看日志 attempt=2 -->

## Screenshots / Recordings
<!-- UI 改动附图; 性能改动附 before/after benchmark -->

## Risk
<!-- 潜在影响, 回滚方案 -->
<!-- 例: "若 retry 触发后 LLM 仍失败, 兜底耗时翻倍, 已加 timeout 兜底; 回滚: 移除 tenacity decorator" -->

## Checklist
- [ ] self-reviewed against [§3 checklist](./docs/团队能力提升方案/04-代码评审流程与机制.md#3-评审清单-checklist)
- [ ] tests added/updated
- [ ] CI green
- [ ] docs updated (if user-facing or architectural)
```

### 9.2 评审评论模板

```markdown
🔴 **BLOCKER**: <file>:<line> <一句话描述>

```go
// 当前
func X() { ... }

// 建议
func X() { ... }
```

原因：<为什么这是 blocker>

参考：<链接到 issue / 文档 / 之前类似讨论>
```

## 10. 度量与改进

### 10.1 度量指标

| 指标 | 目标 | 工具 |
|---|---|---|
| **MR 首响应时间** | ≤ 8h | GitHub API / GitLab API |
| **MR 合入时间** | ≤ 2 工作日 | 同上 |
| **评审者覆盖** | 100% MR 有人评 | 同上 |
| **CI 一次通过率** | ≥ 80% | CI 系统 |
| **P0 逃逸率** | < 5% | 事故记录 |
| **评审评论数 / MR** | 3-15（太少=走过场，太多=需求不清） | GitHub API |
| **Code Review 参与度** | ≥ 60% 成员月评 ≥ 5 个 | GitHub API |

### 10.2 复盘节奏

| 频率 | 内容 |
|---|---|
| 每周 | 团队 standup 过一遍"上周 MR 数据"（首响应时间、卡住最久的 MR） |
| 每月 | 汇总当月 P0/P1 逃逸 + Top 3 常见评审评论 → 决定是否需要新规范 / 新 lint 规则 |
| 每季度 | 全员"评审体验调研"，识别流程痛点 |

### 10.3 持续优化方向

- 把评审中**重复出现**的 MINOR 提炼为 lint 规则（如命名、注释格式）
- 把评审中**重复出现**的 MAJOR 提炼为模板/示例（如错误处理样板）
- 把评审中**很少提到**但重要的检查补到自动化门禁

## 11. 常见反模式

| 反模式 | 表现 | 改进 |
|---|---|---|
| **走形式评审** | "LGTM" 没看代码 | 禁止空评论 LGTM；评论至少 1 条实质性意见 |
| **巨型 MR** | 一个 MR 改 2000 行 | 拆！按功能 / 模块 / 阶段拆 |
| **无限循环评审** | 5 轮还没合 | 设置"3 轮讨论必须线下对齐" |
| **过晚评审** | 提 MR 后 1 周才看 | SLA + 备选 owner |
| **作者消失** | 提完 MR 不回应 | 1 周未回应自动关闭 |
| **不分级评论** | 所有问题都说"必须改" | 用 [§ 5 分级](#5-评审标准分级) |
| **私下合入** | 不走 MR 直接 push | Branch Protection 阻止 |
| **CI 形同虚设** | 红灯也合入 | Branch Protection 强制 |

## 12. 上线 Checklist（每次发布前）

- [ ] 本迭代所有 MR 已合入
- [ ] 所有 P0 逃逸已修复并复盘
- [ ] 覆盖率不低于基线
- [ ] CHANGELOG.md 更新
- [ ] 监控 / 告警就位
- [ ] 回滚预案就位
- [ ] 干系人（PM / 运营）通知到位
- [ ] 生产部署脚本 dry-run 过
