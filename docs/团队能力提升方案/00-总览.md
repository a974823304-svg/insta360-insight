## 一、当前代码质量一图速览

> 详细条目见 [01-代码质量审查报告](./01-代码质量审查报告.md)

| 维度 | 当前状态 | 风险等级 |
|---|---|---|
| 测试覆盖 | **0 个测试文件**（Go / Python / Vue 三端皆 0） | **🔴 P0** |
| 安全（CORS / Auth / 输入校验） | CORS 反射任意 Origin；无 Auth；Filter 无校验 | **🔴 P0** |
| 后端代码异味 | `middleware.go` 手写 `itoa`；`AIService.Generate` 与注释不符 | 🟡 P1 |
| 前端性能 | ECharts 全量引入（~700KB chunk）；按需注册未做 | 🟡 P1 |
| AI 引擎稳健性 | LLM 无重试 / 熔断；`parse_response` 反引号清洗会破坏合法 JSON | 🟡 P1 |
| 工程化工具链 | 无 lint / 无 CI / 无 Dockerfile / 无 pre-commit | 🟡 P1 |
| 命名 / 注释 / 文档 | 整体良好，注释清楚，但缺 ADR / README 标准化 | 🟢 P2 |

### 优先级路线图（建议 4 周落地）

**第 1 周（止血）**
- [ ] 修 CORS 白名单（不能再反射 Origin）
- [ ] 给 AI engine `parse_response` 加严格 JSON 提取 + 反引号保护
- [ ] `middleware.go` 删除手写 `itoa`，用 `strconv.Itoa`
- [ ] `AIService.Generate` 写明 `// TODO: 当前直返 mock，生产应调用 ai-service`

**第 2 周（打底）**
- [ ] 接入 `golangci-lint` / `ruff` / `eslint` + pre-commit
- [ ] Go 后端补齐 `internal/{handler,service,model}` 的单元测试（`httptest` + table-driven）
- [ ] Python AI engine 补齐 `FeatureExtractor` / `PromptBuilder` 单测
- [ ] 加 GitHub Actions CI（lint + test + build）

**第 3 周（加固）**
- [ ] 前端 ECharts 按需引入 + 拆 chunk
- [ ] 后端加 request-id 中间件 + 结构化日志（`slog` / `structlog`）
- [ ] AI engine 加 LLM 重试 + 熔断（`tenacity` / `pybreaker`）
- [ ] 引入 Dockerfile + docker-compose 一键起三服务

**第 4 周（机制化）**
- [ ] 上线代码评审流程（详见 [04](./04-代码评审流程与机制.md)）
- [ ] MR 模板 / Review checklist 落地
- [ ] 团队 1 次技术分享（基于 [03](./03-技术培训计划.md) M5）

## 二、这份方案怎么用

1. **技术 Leader**：先看 [01](./01-代码质量审查报告.md)，把 P0 项排进本周 OKR；其余文档作为团队规范基线。
2. **组员**：先读 [02](./02-团队代码规范与最佳实践指南.md) 全文，存为 wiki 索引；提 MR 前对照 [04](./04-代码评审流程与机制.md) 的 checklist 自检。
3. **新人入职**：按 [03](./03-技术培训计划.md) 对照自己职级 / 短板，挑模块学习 + 实战。
4. **每双月**：重跑一次代码质量审查，更新 [01](./01-代码质量审查报告.md)，看 P0 是否清零、P1 趋势。

## 三、术语

- **P0**：线上会爆 / 数据会错 / 安全漏洞 → 24h 内修
- **P1**：影响可维护性 / 性能 / 团队效率 → 1-2 周
- **P2**：代码风格 / 微优化 / 文档补全 → 持续
- **ADR**（Architecture Decision Record）：架构决策记录，见 [02 § 文档规范](./02-团队代码规范与最佳实践指南.md#文档规范)
- **SLA**（Service-Level Agreement）：评审 / 上线时效承诺，见 [04 § 评审时效](./04-代码评审流程与机制.md#评审时效)
